# M2B: PostgreSQL migration plan

## Scope and constraints

This document designs the migration from the current FastAPI/SQLite persistence layer to PostgreSQL 16 for the current React/FastAPI core commerce flows. It does not change application code, create or alter database objects, run SQL, install dependencies, or migrate data.

The legacy Flask/Vanilla runtime and its `instance/pap.db` database remain outside this migration. The existing SSH tunnel is development connectivity only; production will require application configuration that points to a managed PostgreSQL service without embedding credentials.

## 1. Current SQLite coupling

SQLite is coupled to the current backend in these places:

- `backend/app/config.py` exposes `database_path` and defaults to `backend/data/pap-dev.db`.
- `backend/app/db.py` imports `sqlite3`, opens file connections, sets `sqlite3.Row`, enables foreign keys with `PRAGMA`, and initializes the database by executing `backend/app/schema.sql` at startup.
- `backend/app/schema.sql` is the runtime DDL for `products`, `orders`, `order_items`, and `settings`.
- `backend/app/api/products.py`, `orders.py`, `customer.py`, and `admin.py` type their dependencies as SQLite connections/rows and use SQLite parameter placeholders (`?`), row access, `lastrowid`, `BEGIN IMMEDIATE`, and SQLite upsert syntax.
- `backend/app/serializers.py` expects `sqlite3.Row` objects and reads snake_case columns by name.
- `backend/tests/conftest.py` and `test_orders_contract.py` create/open SQLite files directly for fixtures and stock assertions. Legacy characterization tests intentionally target the separate Flask SQLite database and must not be converted as part of this cutover.
- The development-only `/api/admin/migrate` route reads/writes the `settings` table and performs product upserts, so that compatibility behavior must be retired or explicitly ported before removing the table.

No source changes are proposed in M2B; this list is the M2C implementation boundary.

## 2. Current tables and relations

The current FastAPI schema requires:

| Table | Current purpose | Relations/notes |
| --- | --- | --- |
| `products` | Catalog, stock, product administration | Referenced by `order_items.product_id`; deletion currently sets that reference to null. |
| `orders` | Checkout result and customer/admin order listing | Parent of `order_items`; currently stores a customer snapshot and has no user FK. |
| `order_items` | Immutable order-line snapshot | Belongs to `orders`; product name and price are copied to preserve order history. |
| `settings` | One-time legacy migration marker | Key/value table used only by `/api/admin/migrate`; compatibility/operational, not commerce domain data. |

The target adds `users` for the future account model. The current demo login remains session-only in M2B and must not be silently converted into persistent authentication.

## 3. Target PostgreSQL 16 schema

Use PostgreSQL `bigint generated by default as identity` for new numeric keys, `timestamptz` for timestamps, `numeric(12,2)` for money, `boolean` for flags, and explicit foreign keys/check constraints. Keep the public order identifier as text so existing `PAP-...` IDs can be preserved.

### `users`

- `id bigint generated by default as identity primary key`
- `email text not null`
- `full_name text not null`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`
- `status text not null default 'active'`
- Unique case-insensitive email index: `unique (lower(email))`

This is an account boundary for later work. Passwords, verification, recovery, roles, and session implementation are intentionally not part of M2B.

### `products`

- `id bigint generated by default as identity primary key`
- `name text not null`, `description text not null`
- `price numeric(12,2) not null check (price >= 0)`
- `stock integer not null check (stock >= 0)`
- `category text not null`
- `pet_type text not null check (pet_type in ('cat','dog','both'))`
- `age_group text not null default 'all' check (age_group in ('all','young','adult','senior'))`
- `image_url text not null default ''`, `emoji text not null default '🐾'`
- `featured boolean not null default false`
- `created_at timestamptz not null`, `updated_at timestamptz not null`

Add indexes for the catalog access patterns used by the API, at minimum `(featured, id)` and `(pet_type, age_group, id)` if query filtering remains database-side.

### `orders`

- `id text primary key`
- `user_id bigint null references users(id) on delete set null`
- Customer snapshot fields: `customer_name`, `customer_email`, `phone`, `address`, `district`, `province`, `postal_code` as `text not null`
- `total numeric(12,2) not null check (total >= 0)`
- `status text not null default 'New'`
- `created_at timestamptz not null default now()`

Keep the snapshot fields even after `user_id` exists: an order must remain historically accurate if the user later changes profile data. `user_id` is nullable during the transition because current demo sessions do not create users.

Add indexes on `(user_id, created_at desc)`, `(lower(customer_email), created_at desc)` for the current customer-history fallback, and `(created_at desc)` for admin listing.

### `order_items`

- `id bigint generated by default as identity primary key`
- `order_id text not null references orders(id) on delete cascade`
- `product_id bigint null references products(id) on delete set null`
- `product_name text not null`
- `quantity integer not null check (quantity > 0)`
- `unit_price numeric(12,2) not null check (unit_price >= 0)`
- `subtotal numeric(12,2) not null check (subtotal >= 0)`

Retain product name, unit price, and subtotal as immutable snapshots. The application should validate `subtotal = quantity * unit_price` before insert; a later migration may add a generated column or database-level consistency constraint after compatibility behavior is tested.

### `settings` compatibility table

Retain a small `settings(key text primary key, value text not null)` table only while `/api/admin/migrate` exists. It should not become a general application configuration store. Remove it in a later migration when the legacy migration endpoint and marker are retired.

## 4. Transaction and integrity requirements

Checkout must run in one PostgreSQL transaction. Replace SQLite `BEGIN IMMEDIATE` with a transaction that locks the selected product rows (`SELECT ... FOR UPDATE`), validates stock and authoritative prices, inserts the order and snapshots, decrements stock, and commits. Any validation failure must roll back all order lines and stock changes.

Connection management must use a bounded pool and request-scoped transaction/session handling. Credentials and the complete connection URL come from `.env`/hosting configuration; documentation and Git must contain only a redacted example shape.

## 5. Recommended migration approach

Use **Alembic with SQLAlchemy 2.x and the psycopg 3 PostgreSQL driver**.

Alembic is the standard maintainable migration tool for a FastAPI Python service: revisions are versioned, reviewable, reversible where practical, and runnable independently of application startup. SQLAlchemy supplies PostgreSQL-aware types, transaction/session boundaries, and a gradual replacement for the current direct `sqlite3` API. The first revision should create the target schema; later revisions should add account and operational changes without editing an already-applied schema file.

Do not use startup DDL, `create_all()` as deployment migration, or an ad hoc schema-copy script as the long-term mechanism.

## 6. M2C implementation boundary

M2C will need to:

1. Add pinned `SQLAlchemy`, `alembic`, and `psycopg` dependencies to the backend dependency files; no dependency installation is part of M2B.
2. Replace `database_path` configuration with a `DATABASE_URL` setting loaded from `.env`/hosting configuration, while preserving non-secret test configuration.
3. Replace `backend/app/db.py` with an engine/pool, session dependency, and transaction helpers; remove startup execution of `backend/app/schema.sql`.
4. Add Alembic configuration and an initial revision for `users`, `products`, `orders`, `order_items`, and temporary `settings`.
5. Port API queries and serializers from SQLite row/placeholder behavior to SQLAlchemy models or explicit SQLAlchemy Core statements, including PostgreSQL-safe upserts and `FOR UPDATE` checkout locking.
6. Decide whether `/api/admin/migrate` is ported temporarily or removed before the first PostgreSQL deployment; it must not be left referencing a nonexistent compatibility table.
7. Rewrite backend fixtures and database assertions to use the PostgreSQL test strategy, while keeping legacy characterization tests isolated.
8. Add PostgreSQL integration tests covering schema creation, constraints, transaction rollback, concurrent stock claims, order history, and admin listing. SQLite tests alone are insufficient evidence for the target.

## 7. Later SQLite data migration (not performed in M2B)

The one-time data migration should be a separately reviewed, repeatable command:

1. Freeze writes to the FastAPI SQLite database, take a file backup, and record row counts/checksums.
2. Read SQLite data with a read-only connection and transform timestamps to UTC `timestamptz`, booleans to PostgreSQL booleans, and `REAL` money values to exact decimal strings/`Decimal` before insert.
3. Load products first, preserving IDs where possible; then derive one `users` row per distinct normalized customer email found in orders, leaving `user_id` nullable where identity cannot be safely established.
4. Load orders with their original text IDs and customer snapshots, followed by order items. Preserve nullable product references for deleted products.
5. Load only the required compatibility marker in `settings`, or omit it if the legacy migration endpoint is retired before cutover. Do not migrate secrets or SQLite application settings into PostgreSQL.
6. Reset identity sequences after explicit ID inserts, validate foreign keys, totals, stock invariants, row counts, and representative API responses, then perform a second verification run before enabling writes.
7. Keep uploads as filesystem/object-storage migration work; database migration must copy/validate URLs, not embed binary files.

The migration command must support dry-run/reporting, fail atomically, avoid logging credentials, and be tested against a disposable PostgreSQL database before production use.
